# 🧭 設計メモ: アプリ配布設定（配信ページ「配布設定」トグル）の永続化

> 📌 ステータス: **提案（未実装・要判断）** — 2026-09-26
> 対象: 管理コンソール `/apps` の「配布設定」（自動アップデート / 最低バージョン強制 / テレメトリー収集）

## 1. 🔍 現状

| 項目 | 現状                                                                       |
| ---- | -------------------------------------------------------------------------- |
| UI   | `AppsView.tsx` の `TOGGLES`。React state のみで、再読み込みで初期値に戻る  |
| 保存 | なし（API・DB ともに未実装）                                               |
| 効果 | なし。Editor 側はこの設定を参照していない                                  |
| 表示 | 「表示のみ・未実装」と明記済み（`docs/deployment/app-distribution.md` §7） |

Editor（CivilPDF-Editor v1.12.6）側の実態:

- 🔄 自動更新: `tauri-plugin-updater` が updater Worker の `latest.json` を参照する。コンソールの設定は見ていない
- 🩺 テレメトリー: 診断ログは **端末内保存・オプトイン・外部送信なし**。収集サーバーは存在しない
- 🔢 最低バージョン: Editor が起動時に照会する API は存在しない

⚠️ つまり、コンソール側で保存だけ実装しても**端末の挙動は何も変わらない**。保存するだけの UI は「効いていると誤解させる」リスクがある。

## 2. 🎯 選択肢

| 案                   | 内容                                                                                               | 利点                             | 欠点 / 影響                                                                                     |
| -------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------- | ----------------------------------------------------------------------------------------------- |
| A. 表示を撤去        | トグルを削除し、説明文だけ残す                                                                     | 誤解がなくなる。実装コストが最小 | 将来の機能を示す場所がなくなる                                                                  |
| B. 保存のみ          | `ai_settings` と同じシングルトン行（`apps_distribution_settings`）＋ admin 限定の GET/PUT          | 監査ログに設定変更が残る         | 端末に効かないので誤解は残る。DB migration が必要                                               |
| C. 保存＋Editor 連携 | B に加え、Editor が起動時に `GET /api/v1/apps/policy` を照会し、最低版の強制と自動更新の可否に従う | 実際に効く                       | **Editor 側の改修が必要**（別リポジトリ）。認証方式（端末からの照会に使う資格情報）の設計が要る |

テレメトリーは、Editor の「外部送信なし」方針と矛盾するため、**どの案でも収集は行わない**（C でも「診断ログのオプトイン既定値」の配布に留める）。

## 3. 💡 推奨

1. **短期: 案 A**（またはトグルを無効化して「今後対応」と表示する）。効いていない設定を操作できる状態をなくす
2. **中期: 案 C** を Editor 側の Issue とセットで起票する。コンソール側だけで B を先行させない

## 4. 🔧 案 C を選ぶ場合の設計の骨子（参考）

- 🗄️ DB: `apps_distribution_settings`（`id=1` のシングルトン、`CheckConstraint("id = 1")`）
  - `auto_update_enabled: bool`、`min_supported_version: str`（semver）、`updated_at`、`updated_by`
  - migration は additive（新規テーブルのみ）
- 🔐 API:
  - `GET/PUT /api/v1/apps/settings` — `require_admin`、変更は監査ログに記録
  - `GET /api/v1/apps/policy` — Editor 向け（読み取り専用・最小限の項目）。認証は既存の DX 連携の資格情報を流用するか、別途検討
- 🌐 環境変数 `APPS_MIN_SUPPORTED_VERSION` は、DB 値がない場合の既定値として残す（後方互換）
- 🧪 テスト: RBAC（admin 以外は 403）、semver の検証、監査ログ、`policy` が秘密情報を返さないこと

## 5. ❓ 要判断事項

- 案 A / C のどちらで進めるか
- 案 C の場合、Editor から照会するときの認証方式（主要な認可モデルの変更に当たるかどうか）
